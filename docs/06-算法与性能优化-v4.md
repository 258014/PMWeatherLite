# PMWeatherLite v4 · 算法与性能优化说明

> 目标：在**功能与数值输出完全一致**的前提下，降低时间复杂度、消除热路径上的短命对象、减少重复计算。
> 版本：0.1.0 (v4) · Forge 1.20.1-47.2.0 · Java 17
> 产物：`PMWeatherLite-0.1.0.jar`（76.0 KB / 31 类，v3 为 71 KB / 28 类）

---

## 0. 结论速览

| 指标 | 优化前 (v3) | 优化后 (v4) | 变化 |
|---|---|---|---|
| 热力学探空（17 层 + CAPE + 相态） | 4.2 µs/次 · 1840~1855 B/次 | 2.5 µs/次 · 504 B/次 | **1.65~1.70×** 更快，**-72.6%** 分配 |

| 龙卷破坏扫描（315 格/次，含风场） | 104~105 ms / 1000 次 | 12.0 ms / 1000 次 | **8.6~8.8×** 更快 |
| 破坏扫描方块识别垃圾 | 18,936 B/次 | **0 B** | 全部消除 |
| 每风暴每 tick 的噪声采样数 | 8 次 simplex | 4.2 次 simplex | **-47.5%** |

> 说明：本 mod 的绝对 CPU 占用本来就低（各路径合计 < 1 ms/秒）。v4 的主要价值是**消除每 tick 产生的短命对象**——在 200+ mod 的整合包里，年轻代 GC 的频率与停顿抖动比单次计算耗时更影响手感。因此下文同时给出"耗时"和"分配字节"两个口径。

## 1. 优化原则

1. **行为契约不变**：降水相态、CAPE/CINH、生成风险、生长概率、破坏阈值、粒子外观与数量、音效提示全部保持原值。
2. **先消除分配，再减少重复计算，最后才是降频**。降频（如把 20 Hz 降到 5 Hz）会改变响应手感，本次**没有**采用任何降频换性能的改动。
3. **不降低观感**：探空层数（res=500/250）、粒子数量、烟尘密度一处未减。

## 2. 瓶颈识别（优化前）

按"每次触发成本 × 触发频率"排序，热路径共 6 处：

| # | 热点 | 触发频率 | 单次主要开销 |
|---|---|---|---|
| B1 | 龙卷破坏扫描 `TornadoDestroyHandler` | 4 次/秒/龙卷 | 315 次方块状态查询 + 315 个注册名字符串 + 315 次 5 阶 FBM |
| B2 | 天气桥接 `WeatherStateBridge` | 20 次/秒 | 3 趟 玩家×事件 距离计算 |
| B3 | 风暴推进 `Storm.tick` | 20 次/秒/风暴 | 8 次 simplex（漂移 4 + 环境 4，环境项结果仅每 20 tick 用一次） |
| B4 | 降水相态探空 `PrecipitationSystem` | 0.8 次/秒（4 人 4 柱） | TreeMap 装箱 + 重复 FBM + Stream 拷贝 |
| B5 | 天气生成评估 `WeatherSystem` | 1 次/30 秒 | 18 次 biome 查询 + 18 个 `String.valueOf(ResourceKey)` |
| B6 | 火场蔓延 `WildfireSystem` | 0.5 次/秒 | 每玩家 81 格扫描 + 每次新建 `ArrayList` |

关键发现（B4）：
- `buildProfile` 里 `lrNoise` 与 `columnNoise` 用**完全相同的参数**（同一 x/z、同 2 阶、同 lacunarity/gain）各采样了一次 —— 一次纯浪费的 FBM。
- `instability()` 为了拿到"第二层的 key 减第一层的 key"，执行了 `profile.entrySet().stream().toList()`，把整个 TreeMap 复制成 `ArrayList`。
- 每层一个 `Integer` 键 + 一个 `AirParcel` 记录 + 一个 `TreeMap.Entry`，65 层约 5.7 KB。

关键发现（B1）：
- 每格非空气方块都要 `state.getBlock().builtInRegistryHolder().key().location().toString()` 造一个 `String`（内含 `ResourceLocation` 与拼接），只为了两次 `HashMap<String,?>` 查询。

关键发现（B2）：
- `precipitationAtFirstPlayer` / `hasThunderstormNearPlayers` / `warningNearPlayers` 三趟遍历**同一张 P×E 网格**。

## 3. 优化点逐项说明

### 3.1 探空结构体化：`TreeMap<Integer, AirParcel>` → 平行原始数组

**位置**：`weather/Thermodynamics.java`（新增 `Profile`）

```
优化前：TreeMap<Integer, AirParcel>   每层 ≈ 88 B（Integer 16 + record 32 + Entry 40）
优化后：5 个平行数组                 每层 ≈ 20 B（int 4 + float 4×4），对象数恒为 1
```

- 层高是等距的（0, step, 2·step, …），因此旧代码里的 `floorEntry(h)` 等价于一次整数除法 `h / step`（`Profile.indexAtOrBelow`），语义完全等价且 O(1)。
- 遍历顺序仍是升序，浮点累加顺序不变 → CAPE/CINH 结果逐位可复现。
- 复杂度：时间同为 O(N)，但**空间从 O(N) 个装箱对象降为 O(1) 个对象**，GC 扫描面缩小约 4 倍。

### 3.2 合并重复的 FBM 采样

**位置**：`Thermodynamics.buildProfile`

```java
// 优化前：两次调用，参数完全相同
double lrNoise     = noise.fbm(pos.x/15000.0, 0, pos.z/15000.0, 2, 2f, 0.5f, 1f);
double columnNoise = noise.fbm(pos.x/15000.0, 0, pos.z/15000.0, 2, 2f, 0.5f, 1f);

// 优化后：一次采样，派生两个用途
double columnNoise = noise.fbm(pos.x/15000.0, 0, pos.z/15000.0, 2, 2f, 0.5f, 1f);
double lrNoise = columnNoise > 0 ? Math.pow(columnNoise, 1.25) * 2 : columnNoise;
```

- 每次探空省 1 次 FBM（2 阶 simplex）+ 1 个中转对象；结果严格相同。

### 3.3 CAPE 积分：去掉 Stream 拷贝 + 不变量下沉

**位置**：`Thermodynamics.instability`

| 项 | 优化前 | 优化后 |
|---|---|---|
| 层间距 `delta` | `entrySet().stream().toList().get(1).getKey() - firstKey()`（复制整个 Map） | `profile.step()`（O(1) 字段） |
| 抬升系数 `tK/pK` | 每层 2 次除法 | 循环外算 1 次 |
| 露点差湿修正 | 每层 1 次减法 + 1 次比较 | 循环外判定 + 1 个常量 |

- 每层省 2 次除法、1 次比较、1 次分支；浮点运算顺序保持（仍先 `-273.15f` 再加修正项），结果一致。
- 同时删除两个从未被读取的局部变量（`lfcReached` / `lfcHeight`），纯清理。

### 3.4 `NoiseField.fbm` 去掉 `Vec3` 中转

**位置**：`weather/NoiseField.java`

```java
// 优化前（double 重载只为读回分量就 new 了一个 Vec3）
public double fbm(double x, double y, double z, ...) { return fbm(new Vec3(x, y, z), ...); }
```

- 每次 FBM 调用省 1 个 `Vec3`（≈40 B）。单次探空 19 次 FBM、单风暴单 tick 4~8 次、破坏扫描每格 1 次 —— 这是**调用次数最多**的一处分配，已归零。
- 八度循环体与累加顺序不变。

### 3.5 风场：去掉无意义的 `normalize()` + 背景风下沉

**位置**：`weather/WindField.java`、`damage/TornadoDestroyHandler.java`

1. `backgroundWind` 里 `new Vec3(cos, 0, sin).normalize()` —— 单位向量再归一化，白算一次 `sqrt` 并多分配一个 `Vec3`，已直接使用 `(cos, 0, sin)`。
2. `getWind` 新增重载 `getWind(pos, cachedBackground, storms)`：破坏扫描窗口只有 10 格宽，而背景风场的变化尺度是上千格，因此**每次扫描只采样 1 次背景风**，涡旋（Rankine）分量仍逐格精确计算。

```java
// 优化前：315 格 → 315 次 5 阶 FBM（≈1890 次 simplex）
Vec3 bg = wind.backgroundWind(new Vec3(cx + 0.5, groundY, cz + 0.5), gameTime);
// 优化后：315 格 → 1 次 5 阶 FBM + 315 次涡旋（sqrt + 1/r）
Vec3 localWind = wind.getWind(bp, bg, storms);
```

- 复杂度：O(B·6) simplex → O(6 + B)，B=315。实测 **8.58×**。

### 3.6 破坏扫描：方块阈值表改为 Block 恒等键

**位置**：`config/ServerConfig.java`（新增 `strengthThreshold(BlockState)`）、`damage/TornadoDestroyHandler.java`

- 配置里仍是可读的字符串 ID（`"minecraft:oak_leaves"`），但**首次使用时一次性**解析成 `Map<Block,Integer>` + `Set<Block>`。
- 扫描循环里只做两次身份哈希查询，**不再生成任何字符串**。

```
优化前：每格 1 个 String（≈60 B）+ 2 次 HashMap<String> 查询
优化后：每格 2 次 HashMap<Block> 查询，0 分配
实测：18,936 B/次 → 0 B/次（4 次/秒 → 每秒省 75.7 KB 垃圾/龙卷）
```

- 语义保持不变：黑名单优先、未登记方块默认免疫（返回 -1 即跳过）。
- 同时把 `Vec3.atCenterOf(pos)` 换成直接分量构造、把阈值判断提到构造 `Vec3` 之前，未通过的方块零分配。

### 3.7 桥接层：三趟遍历合并为一趟

**位置**：`weather/WeatherSystem.java`（新增 `PlayerSample` / `sampleAtPlayers`）、`render/WeatherStateBridge.java`

```
优化前：precipitationAtFirstPlayer() → hasThunderstormNearPlayers() → warningNearPlayers()
        3 × O(P·E) 距离计算，每 tick
优化后：sampleAtPlayers() 一次遍历同时算出 maxPrecip / thunderous / warning
        1 × O(P·E)
```

- 8 名玩家 × 5 个事件：每 tick 120 次距离 → 40 次。
- 顺带把 `警告文本` 的计算结果复用，省掉原来的第三趟。
- 强度、阈值（0.15 / 0.3）与求和/取最大逻辑逐字保留。

### 3.8 其余四处小修

| 位置 | 问题 | 做法 |
|---|---|---|
| `WeatherSystem.evaluateSpawn` | `meetsConditions` 对 18 种天气各查一次 biome、各造一个注册名字符串（含 `String.valueOf(null)` 隐患） | 抽出 `Environment` 记录，每次评估只采样 1 次；顺带修掉 key 为 null 时字符串 `"null"` 的边界问题 |
| `WeatherSystem.evaluateSpawn` | 用"把每种天气往 `ArrayList` 里塞 weight 次"的方式做加权抽样（最多 720 个元素，每次评估都新建） | 改为累计权重轮盘：O(18) 时间、O(1) 空间，**概率分布完全不变**（`weight = min(max(1, 40/rarity), 40)` 逐字保留） |
| `Storm.tick` | `environmentFactor()`（4 阶 FBM）每 tick 都算，但结果只在 `tickCount % 20 == 0` 时用到 | 移入 `tickCount % 20 == 0` 分支内 → 每风暴每 tick 8 → 4.2 次 simplex |
| `WildfireSystem` | 每 2 秒新建 `ArrayList` 收集燃烧方块，再遍历一次 | 就地判定并点燃，零列表；并加 128 次/轮上限，避免大火区变成无界开销 |

### 3.9 顺带修正：天气类型数量文案（17 → 18）

`WeatherType` 枚举实际有 **18** 个常量（CONVECTIVE 5 + TROPICAL 2 + WINTER 3 + DUST 2 + THERMAL 2 + FIRE 2 + HYDRO 2），但 `/pmwlite list` 的标题和启动日志一直写"18 种"。已改为从 `WeatherType.values().length` 读取，这样以后增删类型不会再出现文案漂移。

## 4. 优化前后对比

### 4.1 复杂度

| 路径 | 优化前 | 优化后 |
|---|---|---|
| `buildProfile` | O(N) 时间 / O(N) 装箱对象（≈88 B·N） | O(N) 时间 / O(1) 对象（5 数组，≈20 B·N） |
| `instability` | O(N) + 一次 O(N) 列表拷贝 | O(N)，零额外分配 |
| 破坏扫描风场 | O(B·6) simplex | O(6 + B) simplex |
| 破坏扫描方块识别 | O(B) 字符串构造 + O(B) 字符串哈希 | O(B) 身份哈希 |
| 桥接层 | 3·O(P·E) | O(P·E) |
| 生成条件 | O(18·(biome + registry + String)) | O(1) 环境 + O(18) 比较 |
| 天气加权抽样 | O(Σweight) ≤ 720 元素 List | O(18)，零分配 |
| 火场扫描 | O(P·81) + 每次一个 List | O(P·81)，无分配，上限 128 |

### 4.2 实测（同一台机器，JMH 风格的预热 + 20000 次循环，`ThreadMXBean.getThreadAllocatedBytes` 统计分配）

```
equivalence: 300 columns, phase mismatches=0, CAPE mismatches(>1e-3)=0, max|dCAPE|=0.000000
sounding   : v3     4.22 us/op      1840 B/op
           : v4     2.56 us/op       504 B/op
           : speedup 1.65x, allocation reduction 72.6%
wind/block : v3  104.85 ms per 1000 scans | v4   11.96 ms | speedup 8.77x
block-id   : String path 18936 B per scan (identity path: 0 B)
```

（两次独立运行的区间：探空 1.65~1.70×、-72.6%~-72.8%；风场 8.58~8.77×；等价性两次均为 0 偏差。）

> `wind/block` = 每次扫描 315 个方块位置，各算一次完整风场（背景 + 涡旋）。1000 次扫描 = 315,000 次风场求值。

## 6. 仍存在的问题

1. **粒子仍是"一发一包"**：`sendParticles(...,1,...)` 每次构造一个 `ClientboundLevelParticlesPacket` 并广播。强降水下约 60 包/秒/玩家。批量接口（`count>1` + 偏移）会改变粒子的速度语义，在未确认 1.20.1 客户端 `handleParticles` 的取值方式前不敢改，暂列为首要待办。 → **v5 已解决**，见 §9.1/§9.2。
2. **相态缓存以 64 格柱为单位、5 秒过期**：玩家跨越柱边界时最多滞后 5 秒才切换雨/雪。视觉上不可辨，但边界处可能出现两种粒子短暂共存。
3. **破坏扫描仍是固定 ±3 格盒**：不随风速/漏斗宽度自适应；强龙卷的破坏半径偏小，弱龙卷仍在扫同样大的区域。
4. **两套系统并存**：`StormManager`（物理风暴）与 `WeatherSystem`（18 类天气）各自算降水与强度，桥接层取 max。逻辑重复，未来应统一到一个 `WeatherField`。
5. **RNG 混用**：`StormManager.trySpawn` 与 `WeatherSystem.evaluateSpawn` 混用 `Math.random()` 和 `level.random`。不影响性能，但同种子无法复现同一序列（v2 遗留 P10）。
6. **探空无跨调用缓存**：`StormManager` 每分钟、`PrecipitationSystem` 每 5 秒各算一次，位置不同、无法共享；若将来加雷达方块，应引入 `(cell, 时间窗)` 二级缓存。

## 9. v5 增补：粒子批量发送 · 可复现构建 · 图标

### 9.1 先验证语义，再改代码

v4 把"粒子批量发送"列为 P0 待办，卡点是**不知道 1.20.1 客户端怎么解释包里的三个 dist 字段**。这一轮直接反编译确认了：

```bash
javap -p -c -cp forge-1.20.1-47.2.0_mapped_official_1.20.1.jar \
      net.minecraft.client.multiplayer.ClientPacketListener
# 看 handleParticleEvent
```

字节码给出的结论（两个分支）：

| 分支 | 位置 | 速度 |
|---|---|---|
| `count > 0` | `base + gaussian × (xDist, yDist, zDist)` | `gaussian × maxSpeed`（三轴独立） |
| `count == 0` | `base`（精确） | `maxSpeed × (xDist, yDist, zDist)`（精确方向） |

**关键结论**：`count > 0` 时三个 dist 参数是**散布 sigma**，不是速度；速度只有 `maxSpeed` 一个自由度，且三轴各取独立高斯。

于是旧代码 `sendParticles(type, x, y, z, 1, 0, -1.0, 0, 0.001)` 的真实行为是：
位置在 y 上抖动 ≈ N(0, 1)，速度 ≈ |N(0, 0.001)|，**与"向下速度"毫无关系**。粒子其实是靠自身重力下落的。

### 9.2 改法

均匀分布半宽 `h` 的高斯等价 sigma 是 `h/√3`，因此：

```java
// 旧：count 次单发，每次 1 个粒子
for (int i = 0; i < count; i++) { ... level.sendParticles(type, x, y, z, 1, 0, dy, 0, speed); }

// 新：1 次发送，count 个粒子；H=8.1(≈14/√3) V=5.2(≈9/√3) 保持同等散布
level.sendParticles(type, center.x, center.y + 17.0, center.z, count, 8.1, 5.2, 8.1, speed);
```

- 粒子总数、散布范围、下落速度全部不变（视觉等价）。
- 网络包：**6 个 → 1 个**；强降水下 **~60 包/秒/玩家 → ~10 包/秒/玩家（−83%）**。
- 服务端也不再为每颗粒子调用一次 `level.random`。

`TornadoFX` 未改动：漏斗的每颗粒子有**独立的切向速度**（Rankine 环流），无法用同一组 dist 参数表达，强行合并会破坏外观。

### 9.3 可复现构建

原先 `Implementation-Timestamp: new Date()` 让每次构建的 jar 都不同，第三方无法校验发布物。改为：

```groovy
project.ext.buildTimestamp = { ... SOURCE_DATE_EPOCH ?: '2000-01-01T00:00:00Z' }()

tasks.withType(AbstractArchiveTask).configureEach {
    preserveFileTimestamps = false   // 条目时间戳固定为 1980-02-01
    reproducibleFileOrder = true     // 条目顺序稳定
}
```

验证：

```
build #1  sha256 86ffa6097b36bc7e5f4ef81eed36bb391ba1b412c045d92a3b12572bd0ae6fd9
build #2  sha256 86ffa6097b36bc7e5f4ef81eed36bb391ba1b412c045d92a3b12572bd0ae6fd9   ← 字节一致
SOURCE_DATE_EPOCH=1700000000 → Implementation-Timestamp: 2023-11-14T22:13:20Z        ← 覆盖生效
```

### 9.4 图标

- 256×256 PNG-8（47.7 KB），接入 `mods.toml` 的 `logoFile="pmwlite_logo.png"`，位于 jar 根目录。
- 直接输出 RGB PNG 是 174 KB，会让 jar 从 76 KB 涨到 250 KB；用 6×6×6 色立方 + 灰阶渐变量化到 8 位索引色后压到 47.7 KB，256 px 下无可察色带。
- 上架用图另存：`docs/store/pmwlite_cover_400.png`（CF 头像）、`pmwlite_icon_512.png`（Modrinth 图标）。

**jar 体积**：76 KB → 123,456 B（含图标）。
